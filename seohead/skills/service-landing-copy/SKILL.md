# Service Landing Copy — Copy for a Service Page

Goal: write publication-ready copy for a landing page dedicated to one service.
Output format: structured copy blocks, each labeled with its section — they can be inserted into the hero, timeline, gallery, features, FAQ, and CTA components without modification.

---

## Step 0 — Assess Whether a Dedicated Page Is Appropriate

Before writing the copy, assess whether this service warrants a dedicated landing page.

### Criteria for "YES, a dedicated page is warranted"

| Criterion | Evidence |
|----------|---------|
| Demand volume | Target queries receive ≥100–300 impressions/month, or this is a high-ticket B2B niche with low-frequency queries |
| Specific intent | The user is looking for this exact service, not an aggregator |
| Distinct ICP | The audience and pain point differ from those of adjacent services |
| Dedicated conversion path | The service has a specific CTA or funnel |
| Differentiation | You can explain how this service differs from neighboring services in the catalog |

### Criteria for "NO, a catalog card is sufficient"

- Demand is zero or extremely low, with no clear B2B context
- The service is a subset of another service that already has a parent page
- There is no unique angle: the copy would duplicate an adjacent page
- The engagement format has not yet been defined, so there is nothing concrete to promise

> If the answer is "NO," state this explicitly and recommend strengthening the catalog card instead of creating a page.

---

## Step 1 — Gather Service Data

Ask these questions, or extract the answers from the available context:

1. **Service name and URL**
2. **ICP** — who is the customer: B2B / e-commerce / startup / local business?
3. **Primary pain point** — what is going wrong for the customer before they purchase the service?
4. **Outcome** — what does the customer ultimately receive, and how is it measured?
5. **Engagement format** — audit / project / ongoing support / one-off consultation?
6. **Key stages** — what does the delivery process look like (3–6 steps)?
7. **Differentiation** — how does the service differ from competitors' alternatives or adjacent services?
8. **Proof** — are there case studies, metrics, or results?
9. **Objections** — what prevents the customer from making a decision?
10. **CTA** — what is the target action on the page?

If data is missing, ask the user for it or warn that the proof sections will contain placeholders.

## Step 2 — Write the Copy Blocks

Output each block with a section label. The labels are for the developer, who will place the copy in the appropriate UI component (hero, timeline, gallery, and so on).

---

### [HERO] Hero Section

**Purpose:** the first viewport, with 3–5 seconds of attention. One focus, one promise.

```
H1: [the primary offer — what the customer gets, not the service name]
Subheading: [pain point → solution, 1–2 specific sentences]
Lead: [3–4 lines — who it is for, why now, and what will be done]
CTA button: [verb + outcome, such as "Review My Situation" or "Get a Plan"]
Below the button (optional): [risk reversal, such as "no commitment" or "response within 24 hours"]
```

**Rules:**
- The H1 communicates a benefit, not the service name ("Preserve Organic Visibility During a Domain Migration," not "SEO Migration")
- Use "you get," not "we"
- Be specific: not "traffic growth," but "preserve traffic during the migration"

---

### [PROBLEM] Problem Block

**Purpose:** demonstrate an understanding of the pain point. Use it as introductory copy before the features section or as a set of pain-point cards.

```
Section heading: [statement of the customer's pain point / situation]

Pain point 1: [name] — [1–2 descriptive sentences]
Pain point 2: [name] — [1–2 descriptive sentences]
Pain point 3: [name] — [1–2 descriptive sentences]
(3–5 pain points)
```

**Rules:**
- Use the customer's language, not technical terminology
- Each pain point must describe a distinct situation, not rephrase the same issue
- Do not present the solution in this block

---

### [SOLUTION] Solution / Approach Block

**Purpose:** explain the method and why it works. This can appear below the features grid or introduce the timeline.

```
Heading: [exactly how the problem is solved]
Introduction: [2–4 sentences — the principle behind the approach and what distinguishes it from the standard approach]

Principle 1: [name] — [explanation, 1–2 sentences]
Principle 2: [name] — [explanation]
Principle 3: [name] — [explanation]
```

---

### [PROCESS] Delivery Stages (Timeline)

**Purpose:** show the process. The copy goes into a timeline component, with each step presented as a separate card.

```
Section heading: How the Engagement Works

Step 1 — [Stage name]
What happens: [2–3 sentences]
Stage outcome: [what the customer receives at the end]
Timeline (optional): [N days / weeks]

Step 2 — [Stage name]
...
```

**Rules:**
- Use 3–6 steps, with six as the maximum
- Each step is a specific action, not an abstraction
- The stage outcome is a tangible artifact or decision

---

### [FEATURES] What Is Included / What You Receive

**Purpose:** list the deliverables or components of the service. This copy goes into a features grid or an icon list.

```
Section heading: What Is Included in [service name]

Feature 1: [Name] — [1–2 sentences explaining what it is and why it matters]
Feature 2: [Name] — [...]
...
(5–8 features)
```

**Rules:**
- A feature is not a process ("we conduct an audit"), but something the customer receives ("an audit with a prioritized remediation plan")
- Specificity matters more than completeness

---

### [PROOF] Evidence / Case Studies (Gallery or Metrics)

**Purpose:** provide social proof. This copy goes into a case-study gallery, metrics block, or testimonial section.

```
Section heading: Examples of Results

Case study 1:
Industry / site type: [...]
Objective: [...]
Work completed: [2–3 sentences]
Result: [specific metrics and time period]

Case study 2:
...

Metrics (if available):
[N] — [what it represents]
[N] — [what it represents]
```

> If no case studies are available, insert the placeholder `[PLACEHOLDER: add a case study]` and explain to the user what information is needed.

---

### [FAQ] Questions and Answers

**Purpose:** address objections and support GEO optimization. This copy goes into an accordion or Q&A list.

```
Question 1: [the customer's main objection or question]
Answer: [specific, 3–5 sentences, with no filler]

Question 2: [...]
Answer: [...]

(5–7 questions)
```

**Rules:**
- Questions must be genuine, not promotional ("Why are you the best?" is a poor question)
- The first question addresses the most common objection
- Answers resolve uncertainty rather than advertise

---

### [CTA] Call to Action (Final Block)

**Purpose:** provide the final contact prompt. This is a standalone block at the bottom of the page.

```
Heading: [a specific prompt, not "Contact Us"]
Subheading: [what happens after the user responds — 1 sentence]
CTA button: [verb + object]
Risk reversal: [1 line explaining why the first step carries no risk for the customer]
```

---

## Step 3 — Page SEO Parameters

After writing the copy, output:

```
Title: [primary keyword near the beginning + brand, up to 60 characters]
Description: [primary keyword + benefit + CTA, 140–160 characters]
H1: [aligned with the title, but more natural]
Slug: /services/[slug]
Target keyword: [primary]
LSI keywords: [3–5 secondary keywords]
Internal links (suggestions): [which site pages should be linked]
```

---

## Step 4 — Final Checklist

- [ ] Page viability has been confirmed (Step 0)
- [ ] The hero communicates a benefit, not the service name
- [ ] Every block includes a section label
- [ ] The [PROOF] block is complete or contains an explicit placeholder
- [ ] The FAQ addresses genuine objections
- [ ] SEO parameters are included
- [ ] There are no unexplained abstractions such as "comprehensive approach" or "custom solution"
